# 第九章：I/O 设备管理

前面章节已经让应用拥有地址空间、文件和线程。本章把这些能力连接到外部设备：从串口接收命令，把文件写入块设备，将像素显示到图形窗口，并接收键盘与鼠标事件。设备操作不仅涉及寄存器，还要与内核的中断、同步、调度和内存生命周期衔接。

本章使用单 hart、128 MiB 内存的 QEMU RISC-V `virt` 平台。默认图形窗口为 1280×800，GPU 驱动通过设备查询取得实际显示信息。阅读材料为[《rCore-Tutorial-Book-v3》第九章：I/O 设备管理](https://rcore-os.cn/rCore-Tutorial-Book-v3/chapter9/index.html)；下面结合本仓库的 C 接口说明实现。

## 1. CPU 怎样与设备交换数据

轮询、中断和 DMA 分别解决不同的问题。轮询由 CPU 反复检查设备状态，例如等待 UART 发送寄存器可写；中断让设备在事件发生后通知 CPU，例如串口收到字符、块请求完成。DMA 则让设备直接访问指定内存中的数据，CPU 不必逐字节搬运整个数据块。

DMA 可以与轮询或中断组合使用。块设备通过 DMA 读写请求缓冲，启动时可以由 CPU 轮询完成队列，任务运行后也可以通过完成中断唤醒等待线程。因此，“底层提交接口立即返回”和“上层读写接口等待完成后返回”并不冲突：请求提交只把工作交给设备，上层仍要等待设备完成。

设备控制寄存器通过 MMIO 映射到内核地址空间。对这些地址的访问必须遵循寄存器语义；读取 UART 接收寄存器就会取走字符，不能把它当普通内存反复查看。

| 设备 | MMIO 基址 | PLIC 中断号 |
| --- | --- | --- |
| UART | `0x10000000` | 10 |
| virtio-blk | `0x10008000` | 8 |
| virtio-gpu | `0x10007000` | 7 |
| virtio-keyboard | `0x10005000` | 5 |
| virtio-mouse | `0x10006000` | 6 |

PLIC 汇集设备中断。陷入处理先取得中断号，分发到对应驱动，处理后完成 PLIC 中断；设备本身的中断状态也要按底层驱动协议确认。这些控制寄存器只映射给内核。应用通过系统调用使用设备，不直接操作 UART、PLIC 或 VirtIO 寄存器。

## 2. 底层设备操作与内核包装

本章把底层设备协议和与操作系统有关的行为分开。UART 原始接口负责检查寄存器和收发字节；VirtIO 支持层负责 MMIO 握手、特性协商、描述符链、可用队列与完成队列；GPU 底层负责创建图形资源、附加 DMA backing、设置 scanout 和提交显示命令。这些代码均已提供。

操作系统包装层负责把设备操作接到线程与内存管理上：没有字符时让哪个线程等待，完成请求后唤醒谁，等待期间哪些对象必须继续有效，以及应用如何访问设备持有的显存。独立实现的八处接口位于这一层。理解底层与包装层的调用关系即可，不需要重写 VirtIO 协议、DMA 分配或调度器。

## 3. UART：字符缓冲与线程等待

`uart_init` 配置串口并开启接收中断；`uart_write` 在发送寄存器可写后输出字节，采用轮询方式。输入路径通过 `uart_raw_read()` 接收字符，有字符时返回该字节，当前没有字符时返回 `-1`。

串口中断处理把本次可读的全部字符按顺序放入内核 FIFO。若至少收到一个字符，结束设备保护后通知一个等待者；没有新字符就不发通知。中断处理不能等待下一个字符，也不主动切换线程。

标准输入调用 `uart_read`。缓冲不为空时，它从队首取出一个字符；为空时，它在同一个关中断保护区中登记等待，将当前线程设为阻塞，然后结束保护并调用 `sched()`。等待线程再次获得 CPU 后，重新检查缓冲。

检查缓冲与登记等待必须连续受保护。否则，线程可能先看见“空”，中断随后放入字符并发出无人接收的通知，线程最后才进入等待队列；这时缓冲有数据，线程却继续睡眠。`io_wait_no_sched` 将登记等待与实际调度分开，使驱动能够先完成状态登记，再释放设备保护并切换线程。`io_signal` 只把线程加入就绪队列，通知不等于立即运行，也不等于已替线程取出字符。

## 4. 块设备：请求 token 与完成通知

VirtIO 块请求通过描述符链关联请求头、数据缓冲和响应状态。设备从可用队列取得请求，完成 DMA 后写入响应并把请求放入完成队列。token 标识描述符链的起点，驱动用它关联请求和等待者。

全局 `dev_non_blocking_access` 表示运行阶段：

| 阶段 | 标志 | 访问方式 |
| --- | --- | --- |
| 初始化及加载首个程序 | 0 | 提交请求后轮询完成队列，不登记应用线程等待 |
| 调度器开始运行任务后 | 1 | 提交请求，按 token 登记等待，通过完成中断唤醒 |

启动时尚无可阻塞的应用线程，因此提供 `block_sync`。进入运行阶段后，块读写包装接口准备独立响应对象，在同一次关中断保护内提交请求并登记到 `block.condvars[token]`，结束保护后调度。恢复执行时检查响应成功状态，随后才能向调用者返回。不能在驱动中改变阶段标志，也不能用反复 `yield` 替代等待完成中断。

`virtio_block_handle_irq` 消费当前所有完成项，逐一通知对应 token 的条件变量。一次中断可能包含多个完成项，不能只处理一个，也不能唤醒与完成 token 无关的线程。响应状态由恢复后的读写接口检查；提交失败或完成异常沿用 panic 处理。

请求缓冲和响应对象必须活到完成。设备可能仍通过 DMA 访问它们，即使提交函数已经返回，也不能释放内存或提前修改写入源数据。响应对象保留在尚未返回的读写调用栈中，等待结束后再检查，保证设备访问期间地址仍然有效。

设备接口每块 512 字节，文件系统每块 1024 字节；提供的适配层把一次文件系统块访问拆成两次设备块访问。文件系统的可睡眠全局保护和双重间接块支持也已提供，以支撑阻塞 I/O 与 1 MiB 文件。这些是本章运行环境的一部分，不是新增的学生实现任务。

## 5. GPU：共享显存与显示刷新

GPU 初始化查询显示信息，创建二维资源，将设备资源附加到持久的 DMA 内存，并设置显示 scanout。包装层保存帧缓冲指针 `gpu_fb` 和长度 `gpu_fb_len`，调用已有的光标初始化支持。显存由底层 GPU 对象持有；不能用临时数组，或另分配一份像素副本替代这块设备内存。

`virtio_gpu_get_framebuffer` 返回的始终是同一块显存及其长度，不重新分配、清零、复制或映射。用户映射由图形系统调用完成：

| 系统调用号 | 行为 |
| --- | --- |
| 2000 | 将设备帧缓冲映射到当前应用的 `0x10000000`，返回这个用户虚拟地址 |
| 2001 | 调用 GPU 刷新接口，将当前帧缓冲内容提交给显示设备 |

用户虚拟地址与内核 MMIO 地址可以使用相同数值，因为二者使用不同页表。这里应用映射的是 GPU 的 DMA backing，绝不是 UART 寄存器。内核访问和应用访问最终指向同一段物理内存；退出应用时只撤销用户映射，不释放仍由 GPU 持有的显存。

每个像素使用四字节存储，颜色通道按 B、G、R 排列，应用遵循提供的像素格式写入。写入像素与显示更新是两个步骤：`virtio_gpu_flush` 在受保护访问中调用底层传输和刷新操作，检查设备响应。刷新接口不绘制图形，也不重新创建帧缓冲。

## 6. 输入事件与内核协作

键盘和鼠标由提供的 VirtIO 输入驱动管理。设备向已登记的 DMA 缓冲写入 `type/code/value` 事件，驱动处理中断后保存事件并重新提交接收缓冲。系统调用 3000 优先取键盘事件，其次取鼠标事件，当前没有事件时返回 0。系统调用 3001 查询 UART 字符缓冲是否非空；它不消费字符，也不表示键盘设备中的任意按键状态。

外设中断也可能在内核执行系统调用时发生。内核陷入入口保存并恢复上下文，驱动只维护设备状态与就绪队列；真正的线程切换由调度路径完成。就绪队列暂时为空可能表示线程都在等待 I/O，调度器应等待中断，不能据此认定全部程序结束。

关中断保护解决本单核系统中线程与中断处理对软件状态的竞争。它不会停止设备 DMA。描述符与完成队列还需要内存屏障，确保 CPU 发布请求、通知设备及读取完成结果的顺序；这些支持由底层传输层提供。不能用关中断替代 DMA 顺序保证，也不能把内存屏障当成线程等待协议。

进程主线程退出时，提供的清理路径还要协调其他线程及已提交的 I/O：能够取消的等待可以结束，仍有 DMA 访问的请求必须等到完成，才能回收相关线程栈和应用映射。这是内存生命周期保障，不增加本实验的考核项目。
